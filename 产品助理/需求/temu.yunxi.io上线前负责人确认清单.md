# temu.yunxi.io 上线前负责人确认清单

## 背景

项目目标是内部 GPT 车队图片生成网页。主域名 `yunxi.io` 已购买，后续上线网址以二级域名 `temu.yunxi.io` 为准。

本清单只整理上线前需要负责人确认的问题，不代表已经部署、配置 DNS、接入 Secret 或上线。

## 必须负责人确认

### 1. 部署平台或服务器选择

已确认：

- 部署平台/服务器使用 Cloudflare。

仍需负责人确认：

- 谁负责创建和管理 Cloudflare 部署环境；
- 是否需要测试环境和生产环境分开；
- 部署后是否允许直接访问真实图片生成能力。

### 2. DNS 管理与配置权限

负责人需要确认：

- `yunxi.io` 的 DNS 在哪里管理；
- 谁有权限配置 `temu.yunxi.io`；
- 是否允许开发/运维 AI 或内部人员修改 DNS；
- DNS 配置前是否需要二次确认。

### 3. HTTPS/SSL 证书方案

负责人需要确认：

- `temu.yunxi.io` 是否必须启用 HTTPS；
- SSL 证书由部署平台自动签发，还是由域名/DNS/服务器侧单独配置；
- 证书续期由谁负责；
- 证书异常时谁处理。

### 4. 生产环境变量与 Secret 存放方式

负责人需要确认：

- `OPENAI_API_KEY` 存放在哪里；
- `INTERNAL_ACCESS_CODE` 存放在哪里；
- 是否使用部署平台 Secret/环境变量功能；
- 谁有权限查看、创建、更新或删除生产 Secret；
- 是否禁止把 Secret 写入代码、普通配置、日志、Issue、PR、Obsidian 或聊天记录。

必须明确：真实 `OPENAI_API_KEY`、`INTERNAL_ACCESS_CODE`、账号密码、Cookie、Token、API Key 或 Secret 不能进入普通文档和代码。

### 5. 内部访问码规则

负责人需要确认：

- 谁可以访问 `temu.yunxi.io`；
- 是否只允许公司内部人员访问；
- 内部访问码由谁生成和保管；
- 是否需要定期更换访问码；
- 访问码泄露时如何处理；
- 是否需要限制访问次数、IP 或使用范围。

### 6. 批量生成成本上限、限速和失败重试

负责人需要确认：

- 单次批量任务最多允许处理多少张素材图；
- 每张素材最多允许生成多少张结果图；
- 每日或每人是否需要成本上限；
- 是否需要限速，避免短时间大量调用；
- 失败后是否重试；
- 每次失败最多重试几次；
- 失败后跳过还是停止整批任务；
- 成本异常时是否自动停用批量生成。

### 7. 日志和运行数据保存规则

负责人需要确认：

- 是否保存运行日志；
- 日志保存在哪里；
- 日志保存多久；
- 谁可以查看日志；
- 是否保存成功/失败状态、时间、文件名和错误摘要；
- 是否禁止保存完整 prompt、图片内容、账号密码、Cookie、Token、API Key 或 Secret。

建议明确：日志只保存排查问题必要的非敏感摘要，不保存完整提示词和图片内容。

### 8. 回滚方案和故障处理

负责人需要确认：

- 上线后如果出错，谁可以执行回滚；
- 回滚到哪个版本；
- 是否需要保留最近一个稳定版本；
- 服务不可用、生成失败、额度异常、Secret 失效时分别由谁处理；
- 是否需要故障期间临时关闭批量生成功能。

### 9. 是否需要创建 PR

负责人需要确认：

- 是否先创建 PR 再上线；
- PR 由谁创建；
- 谁负责审核；
- 是否需要审核 AI 复核；
- PR 合并是否会触发自动部署；
- 如果合并会自动上线，必须在合并前单独确认。

### 10. 正式上线审批点

负责人需要确认：

- 是否批准配置 DNS；
- 是否批准部署到生产环境；
- 是否批准接入真实 `OPENAI_API_KEY`；
- 是否批准设置真实 `INTERNAL_ACCESS_CODE`；
- 是否批准开放 `temu.yunxi.io` 给内部人员使用；
- 是否批准批量生成功能在生产环境启用；
- 是否需要上线后验证清单和负责人验收。

## 可以默认采用的建议

- 第一版上线只面向内部人员，不开放公开注册；
- 必须启用 HTTPS；
- DNS 配置、生产 Secret 写入、正式部署和上线开放都需要负责人单独确认；
- `OPENAI_API_KEY` 和 `INTERNAL_ACCESS_CODE` 只放在部署平台 Secret/环境变量中；
- 访问码先采用单一内部访问码，后续如需要再升级账号体系；
- 访问码建议上线前设置一次，上线后定期更换；
- 批量生成先设置保守上限和限速，避免成本失控；
- 单张失败默认跳过并记录错误摘要，不中断整批任务；
- 失败重试先设为 0～1 次，避免重复扣费；
- 日志只保存非敏感摘要：时间、任务状态、文件名、成功/失败、错误摘要；
- 不保存完整 prompt、图片内容、账号密码、Cookie、Token、API Key 或 Secret；
- 上线前先做部署预检，再决定是否正式上线；
- 如果创建 PR 会触发自动部署，必须先确认自动部署影响。

## 暂不建议做的事项

- 暂不建议开放给外部用户；
- 暂不建议加入广告、支付、积分、订阅、定价或营销功能；
- 暂不建议保存完整 prompt 或图片内容；
- 暂不建议把真实 Secret 写进代码、`.env` 示例、普通文档、Issue、PR 或聊天记录；
- 暂不建议一开始就做多角色权限后台；
- 暂不建议一开始开放无限制批量生成；
- 暂不建议在未确认 DNS、Secret、访问码、成本上限和回滚方案前直接上线；
- 暂不建议让 PR 合并自动上线，除非负责人已明确批准。

## 下一步建议

1. 负责人先确认部署平台或服务器，以及 DNS 管理位置和配置权限；
2. 再确认生产 Secret 存放方式，包括 `OPENAI_API_KEY` 和 `INTERNAL_ACCESS_CODE`；
3. 同时确认内部访问码规则、批量生成成本上限、限速和日志保存规则；
4. 由开发 AI 做部署预检，但不实际部署、不配置 DNS、不接入真实 Secret；
5. 预检通过后，再由负责人单独批准是否创建 PR、是否部署、是否配置 DNS、是否正式上线。

`temu.yunxi.io` 是后续上线目标域名，部署平台/服务器已确认使用 Cloudflare。但当前仍未部署、未上线、未配置 DNS、未接入生产 Secret。上线前仍必须由负责人确认 DNS 管理位置与权限、生产 Secret 存放方式、内部访问码规则、批量生成成本上限、日志/运行数据保存规则、是否创建 PR 和正式上线审批点。
